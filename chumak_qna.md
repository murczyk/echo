# Chumak Q&A 

## 1. `text`

**Питання:**

```text
1) поле "text" тут довільний формат текту, чи є якість обмеження (чи повинно бути як --текст\n--текст\n)?
```

**Відповідь:**

`text` - це власне текст перехоплення: текстова транскрибація сеансу
радіообміну. Формат з `- текст` або іншими маркерними рядками не є
обов'язковим.

Якщо передано `full_body`, то `full_body` буде основним тілом повідомлення, а
`text` буде використано як очищений текст без службових заголовків
(`body_noheader`). Якщо `full_body` не передано, то `text` буде і основним
тілом повідомлення.

## 2. `freq`

**Питання:**

```text
2) поле "freq" чи може бути масив частот, чи тільки одна частота? 
```

**Відповідь:**

`freq` - тільки одна частота, рядком. Масив частот API не приймає.

Ми не очікуємо, що в одному перехопленні фігурує більше ніж одна частота.

Частота нормалізується ЕХО, наприклад зайві знаки після крапки обрізаються.

## 3. `coords`

**Питання:**

```text
3) поле "coords" обов'язкове? Чи можна передавати пустий масив?
```

**Відповідь:**

`coords` не є обов'язковим. Можна не передавати поле або передати порожній
масив:

```json
{
  "coords": []
}
```

Якщо передати кілька координат, поточна логіка бере першу як основну
координату повідомлення. Координати з тексту повідомлення також можуть бути
розпізнані окремо.

## 4. `from`

**Питання:**

```text
4) поле "from" чи може тут бути масив позивних?
```

**Відповідь:**

`from` - один позивний, рядком. Очікуємо один позивний відправника. Якщо маєте
сценарій на кілька відправників, зверніться до нас.

## 5. `tags`

**Питання:**

```text
5) поле "tags" в прикладі ["БпЛА", "Втрати"] - це довільний текст, чи мітки до чогось у вас прив'язуются в системі?
Нам можна тут надсилати наші теги, чи вони повинні корелювати з вашими?
```

**Відповідь:**

`tags` - масив текстових міток.

Можна надсилати ваші теги. Якщо назва тега точно збігається з увімкненим тегом
в ЕХО, він буде прив'язаний в нашій системі. Якщо такого тега в ЕХО немає,
він не створюється автоматично і не буде прив'язаний як системний тег, але весь
список `tags` збережеться в системі.

Якщо потрібно, щоб теги працювали як ЕХО-теги у фільтрах та інтерфейсі, їхні
назви мають корелювати з наявними ЕХО-тегами; в подальшому можна звернутись
до адміністратора системи і він додасть такі теги як системні.

## 6. `timestamp`

**Питання:**

```text
6) поле "timestamp" це ж час перехвату? Чи це час відправки вам?
```

**Відповідь:**

`timestamp` - час перехоплення, а не час відправки в ЕХО.

API очікує RFC 3339 рядок з timezone. Для UTC використовуйте `Z`, наприклад:

```json
{
  "timestamp": "2026-02-18T08:49:00Z"
}
```

ЕХО зберігає цей час як timestamp повідомлення, а дату і час формує в
timezone `Europe/Kyiv`.

## 7. `sender`

**Питання:**

```text
7) поле "sender": "chumak" тут завжди "chumak" як я розумію?
```

**Відповідь:**

`sender` не зобов'язаний завжди бути `"chumak"`. Це довільний стабільний
ідентифікатор відправника, який буде видно в ЕХО для повідомлень цієї
інтеграції.

Для Chumak можна використовувати `"chumak"` або іншу узгоджену назву. Важливо
тримати її стабільною.

## 8. `full_body`

**Питання:**

```text
8) поле "full_body" є якісь обмеження по формату, чи можна довільний текст?
```

**Відповідь:**

`full_body` - довільний повний текст повідомлення, без спеціальних вимог до
формату. Якщо ви плануєте форматування тексту перехоплення (додавши туди службову інформацію - частоту, список позивних, назву підрозділу противника, dmr метадані тощо) для відправки в месенджер - можете скласти цей відформатований текст сюди, він буде доступний для перегляду в ЕХО.

## 9. `post`

**Питання:**

```text
9) поле "post" обов'язково поле, чи можна ігнорувати? Це вільне ім'я, чи має співадати з вашими?
```

**Відповідь:**

`post` не є обов'язковим, це нащва посту видобування. Його можна не передавати або передати `null`/порожній
рядок.

Якщо передати непорожню назву поста, він буде доступний для перегляду в ЕХО, з можливістю фільтрувати перехоплення за назвою посту, і використовувати назву посту як ознаку для прив'язки перехоплень до радіомережі; особливо корисно якщо в межах однієї смуги один пост чує за частотою Х один підрозділ противника, а інший пост чує за цією ж частотою Х інший підрозділ.

## 10. `unit`

**Питання:**

```text
10) поле "unit" це назва мережі/підрозділу противника? Вона повинна співпадати з іменем вашої мережі, якщо вона знайшлась, чи ми можемо присилати наше ім'я?
```

**Відповідь:**

`unit` - опціональна текстова назва підрозділу або мережі противника. ЕХО парсить це значення і використовує для прив'язки до радіомережі (як одну із ознак, але не ключову), а також для функціоналу фільтрування перехоплень за підрозділами.

Якщо ви вже знайшли мережу через `/api/sigint/network/find-live`, не треба
плутати `unit` і `network`: `unit` лишається текстовою назвою підрозділу, а
DMR/мережеві ознаки передавайте через `network` і `dmr`.

## 11. `locations`

**Питання:**

```text
11) поле "locations" довільне? Чи має співпадати з вашими локаціями в системі?
```

**Відповідь:**

`locations` - масив текстових назв локацій (населені пункти, назви посадок / лісництв тощо). Поле не є обов'язковим і може бути
порожнім. ЕХО зіставляє їх із бібліотекою локацій (наразі підтримуємо тільки населені пункти, решту плануємо додавати в майбутньому).

Кілька локацій будуть об'єднані в один текстовий рядок через кому.

## 12. `group_names`

**Питання:**

```text
12) поле "group_names" це маршрутизація того, в які групи попадають повідомлення у вас в системі? Чи це щось інше
```

**Відповідь:**

Так, `group_names` - це маршрутизація повідомлення в групи ЕХО.
Це відповіддник Signal/WhatsApp груп, для інтеграцій це довільна назва потоку повідомлень, корисно якщо є потреба розбивати потік перехоплень на декілька, із різною аудіторією.

Для `/api/1.1/submit` поле обов'язкове: має бути хоча б одна непорожня назва
групи. Якщо передати кілька груп, повідомлення буде
видиме в усіх цих групах.

## 13. `network`

**Питання:**

```text
13) поле "network" якщо тут знаходиться ваша мережа з вашим іменем і вона співпадає з нашою мережею, то брати ваше ім'я мережі, чи можна наше?
І якщо так станется, що знайшлось декілька мереж, то тут можна відправляти масив, чи тільки одну мережу завжди?
```

**Відповідь:**

`network` - опціональний об'єкт, не масив:

```json
{
  "network": {
    "signal_name": "dmr",
    "cc": 1,
    "name": "УКХ р/м управління 3 мсб 291 мсп 42 мсд 58 А"
  }
}
```

Поточна логіка використовує `network.signal_name` для перевірки, що це `dmr`, і
`network.cc` як DMR color code, якщо детальні `dmr` записи його не дали.
`network.name` приймається, але не є авторитетним ключем для прив'язки до
ЕХО-мережі.

Якщо знайшлася одна мережа, можна передати її назву в `network.name`. Якщо
знайшлося кілька мереж, масив передати не можна: оберіть найімовірнішу мережу
або не передавайте `network.name`. ЕХО все одно рахує прив'язки мереж на своїй
стороні за ознаками повідомлення.

## 14. `dmr`

**Питання:**

```text
14) поле "dmr" обов'язкове? Чи можна надсилати пустий масив? Просто не дуже розумію, що сюди потрібно вносити
```

**Відповідь:**

`dmr` не є обов'язковим. Можна не передавати поле або передати порожній масив:

```json
{
  "dmr": []
}
```

У `dmr` варто передавати деталізовану DMR metadata, якщо вона у вас є:

```json
{
  "timestamp": "2026-02-18T08:49:00Z",
  "cc": 1,
  "freq": "404.1350",
  "signal_name": "dmr",
  "sender_id": 110,
  "sender_name": "ЯРУС",
  "call_group_id": 50,
  "call_group_name": "СВЕТЛЫЙ",
  "hash_id": "2324d327"
}
```

Для кожного `dmr` запису обов'язкові `timestamp`, `freq` і `signal_name`.
`signal_name` зараз підтримується тільки як `"dmr"`. `cc`, `sender_id`,
`sender_name`, `call_group_id`, `call_group_name`, `hash_id` опціональні.

Якщо `dmr` порожній, але є `network.cc`, ЕХО збереже тільки color code як
metadata.
