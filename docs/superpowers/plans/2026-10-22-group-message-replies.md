# Group Message Replies Implementation Plan

Задача: [#3612](https://github.com/echoua/echo/issues/3612).
Оновлено 2026-10-24 після перевірки сценаріїв і фронтенд-виправлень.

## Обсяг

Тільки `/rer-duty-neo` та `/rer-analysis-neo`. Поточні доробки — лише фронтенд,
без змін Rust/API/міграцій. Спільний ланцюжок уже реалізовано. Native reply із
Signal/WhatsApp входять у цю саму модель.

Від’єднання у create/edit, відповідні гонки E11–E13 та підвантаження списку
частинами виключено з поточних вимог і тестів. Не додаємо приєднання наявних
повідомлень, merge/move, зміну цілі чи окремий режим/вкладку Аналізу.

## Наявний контракт

- `POST /api/rer-importer/message-replies`: `{signal_message_ids, screen}` →
  `{replies, reply_messages}`. До 512 ID карток на запит; повертаються всі зв’язки
  зачеплених ланцюжків, із `thread_id` та окремими прапорцями видалення кінців.
  Це не пагінація учасників. Читання використовує індекси ланцюжків.
- `submit-direct` приймає один `engaged_message_id`: фактично вибране джерело.
  Зв’язок і повідомлення зберігаються в одній транзакції; root нормалізується
  бекендом. Видалення root не розриває зв’язки між іншими учасниками.
- `ReplyStore` батчить mounted-картки, обмежує кеш, відкидає застарілі відповіді
  й оновлюється через чинний polling coordinator та `ETInboxChanged`.
- Бекенд повертає порядок `(message_reply.created_at, message_reply.id)`.
  Фронтенд сортує доступні повідомлення за `(CitedMessage.createdAt, id)` — датою
  створення саме повідомлення в Echo, незалежно від часу перехоплення чи зв’язку.
  Оригінал також бере участь у сортуванні; лейбл не закріплює його першим.
  Для deleted/unavailable API не передає дату створення: позначки зберігають
  свої позиції у відповіді. Строгий порядок цих позначок після reload потребує
  доповнення бекенд-контракту й не входить у поточні frontend-зміни.

Деталі: [message-replies.md](../../message-replies.md).

## Сценарії E1–E10

Reply — окреме звичайне повідомлення. Текст/вкладення порожні, решта defaults
звичайні; група джерела зафіксована, зокрема у «Всі групи». Після успіху editor
закривається без автоматичного переходу.
Кнопка reply та редактор доступні лише з правом створення повідомлень;
користувачі лише з правами перегляду можуть читати ланцюжки й переходити між повідомленнями.

- E1: перший reply із групи та «Всі групи», рамка джерела, взаємні посилання,
  заблокована група.
- E2: reply на групове розвіддонесення створює звичайне повідомлення; його
  report-parent/copy зв’язки не успадковуються.
- E3: A створює оригінал, B відповідає, C відповідає B, A знову відповідає
  оригіналу. Усі бачать спільний ланцюжок у порядку створення повідомлень.
- E4: незалежні ланцюжки однієї групи не змішуються.
- E5: одночасні перші reply утворюють один ланцюжок без дублів; порядок стабільний.
- E6: 10 000+ історичних повідомлень, 100 учасників, максимум 2 інші повідомлення
  на картці; «Усі повідомлення N» відкриває весь доступний список поверх картки зі своїм scroll,
  без зміни її висоти. Далекий перехід у тому самому фіді; інша Duty-колонка
  зберігає своє положення. Чанків і запитів сторінок при scroll немає.
- E7: фільтри й період зберігаються; target поза фільтрами позначено, для перегляду
  користувач змінює фільтри сам. Нові reply виконують звичайні правила групи,
  видимості й unread.
- E8: актуальне прев’ю після редагування іншим користувачем; текст reply і
  порядок створення не змінюються.
- E9: видалення root/middle/last лишає позначку без вмісту й зберігає інших
  учасників та можливість відповідати на доступні повідомлення.
- E10 (уточнено): після успішного оновлення цитати недоступного джерела під час
  написання першого/вкладеного reply показати пояснення і зберегти як звичайне
  повідомлення без `engaged_message_id`. Зберегти текст, вкладення й групу;
  нового учасника чи tombstone для цього повідомлення не створювати.
  Наявний старий ланцюжок і його позначки видалення лишаються.

## Фронтенд

- [x] Спільний responsive editor, source outline, locked group, close-on-success.
- [x] Єдина перевірка права створення для звичайного повідомлення і reply;
  desktop/mobile дії приховані для viewer-ролей.
- [x] Reply — друга дія картки; «Ланцюжок» має колір і прозорість часу створення;
  однорядкове клікабельне прев’ю без дати, часу й лейбла оригіналу.
  У попапі — основний колір заголовка, дата `DD.MM.YYYY · HH:mm` та вертикальний
  степпер без номерів; лейбл оригіналу також відсутній.
- [x] Максимум 2 останні інші повідомлення за часом створення в Echo; бейдж лише на «Усі повідомлення N», коли
  в ланцюжку більше 2 повідомлень; попап включає поточне повідомлення.
  Popover має власний обмежений scroll, без розтягування картки й пагінації.
- [x] Перехід у поточному фіді/початковій Duty-колонці без зміни фільтрів;
  найновіше повідомлення не залишає штучного порожнього місця внизу.
  Повторний перехід перезапускає підсвітку; поки ціль зафіксована, layout в Аналізі
  не запускає підвантаження, яке могло б витіснити її з вікна.
- [x] E10: прибирати зв’язок з недоступним джерелом при формуванні payload,
  перевіряючи останній стан також після завантаження вкладень. Без додаткового
  обходу історії чи запиту на кожну картку.
- [x] Зберегти synchronous in-flight guard і disabled submit. Після мережевої
  помилки, 500 чи 403 показати помилку й зберегти draft/зв’язок; не повторювати
  запит і не переходити автоматично до ordinary create за самою помилкою.
- [x] Звірити решту acceptance assertions із поточним UI: компактне прев’ю не показує
  поточне повідомлення, попап показує весь ланцюжок; кнопка з’являється від
  3 учасників. Бізнес-сценарії не послаблювати через відсутню реалізацію.
- [x] E7: показувати позначку target поза фільтрами до переходу. Перевіряти тільки
  ID учасників через наявний matching-filters API, пакетами до 100 ID на фід,
  зі спільним обмеженим кешем і скиданням результатів при зміні фільтрів.
- [x] Збереження чернетки: effect парсера читає актуальні значення форми;
  запізнілий effect із порожнім snapshot не скидає введений текст.

## Перевірка та межі

- Оновити E6/E10 під погоджену поведінку. Перевірити браузером обидва Neo-екрани,
  повторне відправлення під час save, відсутність автоматичного retry після
  невизначеного результату, збереження чернетки, наявні reply/navigation регресії.
- Форматування змінених TS/TSX, TypeScript, відповідні frontend-тести й
  `just build-front`. README overviews не змінювати.
- Фікстура around-message відтворює контракт API: хронологічне вікно,
  до однієї сторінки до і після цілі та відповідні лічильники.
- Backend DB-тести не підміняти моками: браузерні сесії не доводять DB concurrency.
- Source-deleted validation зараз може бути generic 500. Якщо джерело видалене
  між останнім refresh і серверною перевіркою, не робити небезпечний повтор:
  залишити draft до актуалізації даних і наступної дії користувача.
- Backend-питання поза цією ітерацією: request-level idempotency після невідомого
  commit, вимірювання global advisory lock під навантаженням, точна фіксована
  група без серверного fallback. Зміни або вимірювання реального середовища
  потребують окремо погодженого обсягу й дозволу на операцію/target.
