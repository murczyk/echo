# Спільна транскрибація повідомлень і аудіо пристроїв

Повний ключ об’єкта в налаштованому S3 bucket визначає джерело. Таблиця
`wd.transcription_source` містить лише `id UUID PRIMARY KEY` та
`source_key TEXT NOT NULL UNIQUE`. `echo_gpu_transcription_queue.source_id`
посилається на цей UUID за домовленістю застосунку. Схема native-черги та
версія `echo-gpu-client` не змінюються. ID матеріалу, джерела й задачі —
окремі ідентичності.

Однаковий ключ дає одну native-задачу й один результат. Однакові байти за
різними ключами дають різні задачі. Bucket, доступ і StrongBox-ключ беруться
з поточної конфігурації; у реєстрі немає URL, credentials чи типу власника.
Зміна bucket потребує окремого перенесення даних.

## Постановка та виконання

Реєстрація джерела й native enqueue відбуваються в одній wd-транзакції.
Повторення enqueue не скидає спроби, помилку, готовий текст або аудит.
Адаптер читає UUID → ключ → S3, без звернень до таблиць повідомлень чи
пристроїв. StrongBox визначається за magic envelope, AAD — `bucket/full-key`.
Помилка автентифікації не допускає трактування ciphertext як plaintext.
Після обмеженого читання аудіо перевіряється ffprobe й записується у приватний
тимчасовий файл. Межа plaintext — 100 MiB.

Виконавець утримує exclusive advisory lock окремою сесією. Native SQL
використовує пул із двома з’єднаннями, щоб heartbeat міг виконуватися, поки
work очікує SQL. Кожна фізична сесія пулу утримує shared drain lock.
Наступний виконавець бере цей drain lock ексклюзивно перед recovery, тому
не може почати роботу, поки попередні SQL-сесії ще здатні записувати результат.
Втрата leader або data-сесії закриває весь пул; runner створює нового
виконавця, який спочатку відновлює stale спроби й чекає завершення lease
свіжої попередньої спроби. Автоматичного продовження старої спроби через
нове з’єднання немає. Усі standalone runners використовують ту саму фабрику.
Адміністративний клієнт звичайного пулу не виконує claim. SQL-транзакція
не утримується під час GPU HTTP.

Політики native client: до 8 спроб, вік до 24 годин, затримка 5–300 секунд,
heartbeat кожні 15 секунд, stale після 120 секунд. Загальний перемикач
призупиняє наступні claims. Ліміт одного виконавця стосується чинної
native-спроби; fence не є підтвердженням завершення загубленого HTTP-запиту
на віддаленому GPU. Старий device `outcome_unknown`/операторський слот більше
не використовується.

## Повідомлення

Ключ вкладення — чинний `media_object_key` з префіксом `message-media/`.
Постановка перевіряє тип, розмір і налаштування як раніше. Пакетне читання
зіставляє media IDs з ключами й повертає готові результати за вихідними
media IDs. Воно не чекає підтвердження доставки або проєкції результату.
Цей шлях спільний для карток, Аналізу, Оперативного, звітів та Iggy.

Native completion сповіщає пов’язані повідомлення через наявний inbox
fanout у domain runner. Існуючий Iggy trigger черги збережено; його функція
знаходить повідомлення через ключ. OCR та інші media-result випадки
зберігають своє зіставлення за media UUID. Адмінсписок результатів лишається
обмеженим повідомленнями; за відсутності назви він показує ключ джерела.
Загальні лічильники черги охоплюють також аудіо пристроїв.

## Пристрої

Публікація зберігає `automatic_transcription_pending=0` у тому самому
files commit, що й `device_audio`. Native enqueue виконується після цього
commit. Падіння процесу між цими діями не втрачає допуск.

Device sync обходить pending записи обмеженими сторінками за ID й читає
native source/state/count пакетом. Активні задачі з достатнім лічильником
пропускаються без блокувань окремих source/audio; reset і застосування
результату завжди повторно перевіряють актуальний стан під блокуванням. Значення pending:

- `NULL` — незавершеної локальної синхронізації немає;
- `0` — забезпечити native-задачу та застосувати її результат;
- `n+1` — дочекатися щонайменше native `reprocess_count=n+1`.

Маркер не очищується після enqueue. Після успіху один files commit записує
`automatic_transcription`, native `finished_at` у `automatic_transcribed_at`
та pending NULL. No-speech має текст NULL і заповнений час. Terminal очищує
pending, залишаючи попередні автоматичні текст і час. Детальна помилка
залишається у native-черзі/адмінці. Збій files commit залишає маркер:
наступний цикл повторює локальне збереження без нового inference.

Текст завжди читається з `device_audio`. Готовий текст/no-speech не потребує
native lookup. Авторизація, видимість пристрою й налаштування все ще
потребують wd. Діагностика pending/невдалої спроби може окремо читати чергу;
її недоступність не підміняє локальний текст і не ламає details.
Ручний текст, чернетки, `text_version`, processed і його версія незалежні.
Після кінцевого стану фронтенд припиняє polling; повторне відкриття чи явне
оновлення перечитує snapshot, зокрема після дії в іншій сесії.

Локальне вимкнення й вимкнення розділу забороняють новий допуск. Уже
прийнята робота завершується. Архівація/видалення забороняє локальне
застосування; готовий старий текст не стирається. Звичайне відкриття не
скидає terminal, completed або no-speech.

## Явний повтор

Усі повтори проходять спільну domain-координацію. Під lock рядка джерела
спочатку files commit фіксує ціль n+1 для пов’язаного device audio, потім
native reset змінює ту саму задачу. Поки pending не завершено, повторні
команди об’єднуються. Після завершення pending нова явна команда є новим
повтором. HTTP exactly-once без request token не обіцяється.

Якщо процес упав перед reset, sync виконає його за збереженою ціллю. Якщо
reset уже стався або новий результат встиг завершитися, лічильник не
збільшується повторно. Відсутня native-задача при pending>0 — операційна
помилка, а не підстава створити новий цикл. Порядок блокувань:
wd source → files audio. Новий target не може бути стертий старим batch.

Увімкнення налаштування саме не сканує історію.

## Перенесення та відновлення

Перенесення виконує звичайна SQL-міграція разом з іншими міграціями.
Окремої prepare-команди немає. Порядок переходу:

1. Зробіть узгоджені резервні копії wd, wd_files, S3 та конфігурації ключа.
2. Зупиніть API, bgworkers, socket activation і oneoffs. Не допускайте
   змішаних версій: advisory locks не захищають від старих виконавців.
3. Застосуйте міграції обох БД новим binary:
   `wdintel-rs --mode=live migrate`.
   Міграція `m20261017_135230_migrate_transcription_sources` в одній
   транзакції wd реєструє ключі та замінює media UUID на registry UUID
   у source_id. Вона не звертається до wd_files, S3 або GPU.
4. Запустіть тільки нові processes. Перевірте повідомлення, пристрій,
   локальне збереження тексту та native counters.

За одного завдання на ключ зберігаються всі native поля, крім source_id,
включно з текстом, станом, спробами, timestamps, кешем і reprocess audit.
Кілька завдань на один ключ об’єднуються лише тоді, коли всі completed,
тексти побайтово однакові (включно з NULL для no-speech), а решта даних
сумісна. Залишається найраніше завдання за (created_at, id).
Допустимі відмінності історії: IDs, created_at, updated_at, finished_at,
started_transcription_at, transcription_scope_id, selected_audio_id,
actual_instance_id та worker_id. Інші поля, зокрема attempts,
selected_audio_checksum і reprocess audit, мають збігатися.
IDs та історія зайвих дублів видаляються; текст повідомлень зберігається.

Відсутній ключ або несумісні дублікати зупиняють міграцію з конкретними
IDs і ключем до зміни durable data. Помилка запису відкочує всю
транзакцію; повторне застосування безпечне. Технічний remap не створює
Iggy-подій і не викликає enqueue/reset. Міграція тимчасово блокує записи
в queue, registry і media; очікування блокування обмежене п’ятьма секундами.

Старі device jobs і таблиці бекфілу видаляються owning files migrations
без перенесення. Збережені тексти аудіо та налаштування залишаються.
Сканування історичних аудіо й повторного розпізнавання немає.
Startup застосовує міграції перед запуском воркерів, крім режиму
`is_slave`, де їх спершу має виконати primary. Startup, воркер і окрема
команда бекфілу повідомлень відмовляють за неконвертованої черги.

Перехід підтримує наявну чергу з main. Сумісності з відкинутими
проміжними схемами гілки (inputs, bindings, pins і migration-state) немає.
Rollback потребує узгодженого snapshot; повернення лише старого binary
недостатньо. Зворотна міграція даних навмисно не підтримується.

Зареєстровані об’єкти та native rows автоматично не видаляються. Published
аудіо утримується також до реєстрації, щоб видалення не змагалося з новим
власником. За недоступності реєстру cleanup відкладається. Online GC
зареєстрованих джерел — окрема задача; pins/tombstones для цього не додано.
