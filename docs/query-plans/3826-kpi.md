# Hourly KPI query review (#3826)

Local PostgreSQL plan evidence collected on 2026-11-04 with
`EXPLAIN (ANALYZE, BUFFERS, TIMING OFF, SUMMARY ON)` and a 10-second statement
timeout. Fixtures used temporary tables in the dedicated
`wd_test_3826_review` database and were rolled back. No real environment changed.

This is synthetic scale evidence, not measured production workload or a Greptime
benchmark. Before enabling collection, verify plans and sustained query load on
the approved rollout target as described in [QUERY_PERF.md](../../QUERY_PERF.md).

The fixtures contained 100,000 accounts, 100 organisms, 1,000,000 retained
reports, and 500,000 notification jobs distributed over 365 days. Reports used
eight kinds, up to 100,000 distinct authors, and 95% successful requests. Jobs
were 95% sent. The report fixture included the existing `(created_at DESC,
id DESC)` index and the account joins included primary-key indexes. Notification
history had no creation-time index, matching the migration catalog. Tables were
analyzed before measurement.

Report plans used a bitmap index scan with **both** time bounds under `Index Cond`.
They read 19,180 / 82,200 / 246,600 matching requests for 7/30/90 days. The metrics
path used the shared report SQL with author/day aggregates disabled; those plan
branches were never executed. This also avoids the dashboard's 10,000-author
result cap. The larger windows still spilled materialized CTE/percentile work to
temporary storage, so production temporary I/O remains part of rollout review.

The all-time report count scanned retained reports, and notification queries
scanned all 500,000 jobs. These existing dashboard access paths remain bounded
by the read-only transaction's 10-second statement timeout. No new index or
replication-impact declaration is introduced by this branch. Larger retention
volumes may make these sources unavailable; collection must not trigger an
automatic schema change or mirror resync.

API observations retain the dashboard's six-hour host/time predicates. Reusing
identical successful or empty slices within a refresh reduces healthy
7/30/90-day collection from 508 reads to 360. Each source/window keeps a
five-minute total budget; failed or incomplete reads publish availability zero.
The observation regression exercises production queries against local PostgreSQL
temporary tables with the `string` cast type provided by a temporary domain; it
does not establish Greptime production query cost or retention completeness.
