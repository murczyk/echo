# Авторизація та запити до Echo REST API

Інструкція для розробників зовнішніх інтеграцій. Актуальна станом на 13.10.2026.

Echo використовує сесійну cookie: клієнт надсилає логін і пароль, отримує cookie
у відповіді та передає її в наступних запитах до того самого сервера.

## 1. Що потрібно отримати від адміністратора

- Базову HTTPS-адресу потрібного сервера Echo, наприклад
  `https://echo.example.org`, без кінцевого `/` і без `/api`.
- Логін і пароль окремого облікового запису для інтеграції з роллю `Api`.
- Перелік доступних інтеграції API-методів та потрібні права на дані.

Обліковий запис і його організація мають бути активними, а вхід за паролем —
увімкненим. Роль `Api` дозволяє виконувати вхід без інтерактивної двофакторної
автентифікації. Доступ до конкретних методів, груп і даних залежить від прав
облікового запису; сама авторизація не надає доступу до всіх даних Echo.

Нижче наведено команди для Bash і `curl` версії 7.76 або новішої.
`https://echo.example.org`, `integration-api` та `YOUR_PASSWORD` — приклади;
замініть їх на отримані від адміністратора значення. Виконуйте команди в одному
терміналі та робочому каталозі.

## 2. Отримати й зберегти cookie

Задайте адресу сервера та створіть файл `login.json` із даними для входу:

```bash
umask 077
export ECHO_BASE_URL='https://echo.example.org'

cat > login.json <<'JSON'
{
  "user": "integration-api",
  "password": "YOUR_PASSWORD"
}
JSON
```

Поле з логіном називається **`user`**. Надішліть цей JSON на
`POST /api/user/login`:

```bash
curl --silent --show-error --fail-with-body \
  --cookie-jar echo-cookies.txt \
  --header 'Content-Type: application/json' \
  --data-binary @login.json \
  "$ECHO_BASE_URL/api/user/login"
```

Успішний вхід повертає HTTP `200`, заголовок `Set-Cookie` та JSON-рядок:

```json
"Authenticated"
```

`--cookie-jar echo-cookies.txt` зберігає cookie у файл. Її значення береться із
заголовка `Set-Cookie`, а не з тіла JSON-відповіді. Цей файл потрібен для наступних
запитів.

Якщо замість `"Authenticated"` повернувся об'єкт із `Needs2fa` або
`Needs2faSetup`, вхід потребує другого фактора й ще не завершений, навіть за HTTP
`200`. Для автоматичної інтеграції зверніться до адміністратора, щоб він перевірив
роль `Api` виданого облікового запису.

## 3. Перевірити сесію

Надішліть збережену cookie на `GET /api/user`:

```bash
curl --silent --show-error --fail-with-body \
  --cookie echo-cookies.txt \
  --cookie-jar echo-cookies.txt \
  "$ECHO_BASE_URL/api/user"
```

Успішна відповідь — HTTP `200` та JSON з інформацією про поточного користувача,
зокрема `name` і `roles`. Перевірте, що `name` відповідає виданому логіну, а
`roles` містить `Api`.

`--cookie` читає cookie з файлу та додає її до запиту. `--cookie-jar` зберігає
оновлені cookie з відповіді. Використовуйте обидва параметри в наступних запитах.

## 4. Виконувати запити до REST API

### GET: отримати довідник тегів

Для облікового запису з роллю `Api` доступний `GET /api/1.1/tags`:

```bash
curl --silent --show-error --fail-with-body \
  --cookie echo-cookies.txt \
  --cookie-jar echo-cookies.txt \
  "$ECHO_BASE_URL/api/1.1/tags"
```

Відповідь — JSON-масив тегів. Аналогічно `GET /api/1.1/settlements` повертає
довідник населених пунктів.

### POST: знайти активні мережі за частотою

Приклад запиту до `POST /api/sigint/network/find-live`:

```bash
curl --silent --show-error --fail-with-body \
  --cookie echo-cookies.txt \
  --cookie-jar echo-cookies.txt \
  --header 'Content-Type: application/json' \
  --data-binary '{"freq":"404.1350","color_code":"1"}' \
  "$ECHO_BASE_URL/api/sigint/network/find-live"
```

`freq` — частота в МГц, передана рядком; `color_code` — необов'язковий параметр,
також рядок. Метод повертає об'єкт із масивом `networks`, враховуючи доступ
облікового запису до даних. Відповідь `{"networks":[]}` означає, що доступних
мереж за умовами пошуку не знайдено.

Для інших методів використовуйте той самий механізм cookie, але узгоджені для
конкретного методу HTTP-метод, шлях і JSON-поля. Наведені GET- і POST-запити
читають дані; для створення або зміни даних потрібен відповідний метод API.

## 5. Як передавати cookie у власному HTTP-клієнті

Увімкніть сховище cookie (cookie jar) та використовуйте той самий HTTP-клієнт
для входу й наступних запитів. Клієнт має зберігати cookie із заголовків
`Set-Cookie` і передавати їх у заголовку `Cookie`, враховуючи домен, шлях,
строк дії та атрибут `Secure`.

Якщо заголовки обробляються вручну, схема виглядає так:

```http
Set-Cookie: id=<значення-cookie>; Path=/; Secure; HttpOnly; SameSite=Lax
```

У наступному запиті:

```http
Cookie: id=<значення-cookie>
```

Це схема, а не готові значення: використовуйте фактичну назву та повне значення
cookie, отримані від сервера, без змін. Атрибути `Path`, `Secure`, `HttpOnly`,
`SameSite`, `Expires` та `Max-Age` не копіюються в заголовок `Cookie`. Якщо сервер
видав кілька потрібних cookie, передавайте їх як `name1=value1; name2=value2`.

Cookie передається в заголовку `Cookie`; заголовок `Authorization: Bearer ...`
для цього способу входу не використовується. Надсилайте її лише до сервера Echo,
який її видав, через HTTPS. Зберігайте оновлення `Set-Cookie` з подальших
відповідей.

## 6. Помилки та повторна авторизація

| Відповідь | Що перевірити або зробити |
| --- | --- |
| HTTP `400` під час входу | Перевірити JSON-поля `user` і `password`, правильність облікових даних, активність облікового запису та дозвіл на вхід за паролем. Прочитати тіло відповіді. |
| HTTP `401` | Cookie не передана, сесія завершилась або стала недійсною, чи обліковий запис деактивовано. Виконати вхід повторно та перевірити `GET /api/user`; якщо помилка лишилась, звернутися до адміністратора. |
| HTTP `403` | Обліковий запис не має потрібних прав. Узгодити права з адміністратором. |
| HTTP `404` | Перевірити адресу сервера, шлях API та доступність методу в установленій версії Echo. |
| HTTP `429` | Перевищено ліміт запитів. Зачекати кількість секунд із заголовка `Retry-After` перед повторною спробою. |
| HTTP `5xx` | Зберегти час, метод, шлях запиту й код відповіді та передати адміністратору для перевірки. |

Сесія має обмежений строк дії. Після `401` отримайте нову cookie через
`POST /api/user/login`. Якщо повторний вхід неуспішний, не запускайте нескінченний
цикл авторизації. Для запиту, який створює або змінює дані, перед повторним
надсиланням перевірте правила ідемпотентності відповідного методу, особливо після
таймауту або втрати з'єднання.

Для ролі `Api` типовий ліміт — 2 запити на секунду з можливістю короткого
сплеску до 5 запитів; адміністратор може змінити ці значення. Ліміт спільний
для запитів одного логіну, включно з кількома його сесіями. Повторний вхід
не є способом обійти ліміт.

Файли `login.json` та `echo-cookies.txt` містять облікові дані: не додавайте їх
до репозиторію, не включайте у звіти й не передавайте разом із цією інструкцією.
Не записуйте пароль і значення cookie в журнали інтеграції. Після завершення
ручної перевірки видаліть локальні файли, якщо вони більше не потрібні:

```bash
rm -f login.json echo-cookies.txt
```

Видалення локального файлу не завершує сесію на сервері.
