## Implemented follow-up

The 3826 follow-up exposes four tabs with implemented metrics: account base, activity, speed, and technical quality. KPI is the last entry in `Адмін → База знань`. Missing-data and definition notes belong in this backlog, without dashboard blocks or tabs containing only these notes. Login problems, onboarding, feature adoption, retention, channels/bots, and referrals have no implemented metrics and remain hidden. Undefined work remains out of scope for this iteration, as confirmed by the product owner.

- [x] Admin-only bounded KPI read APIs: `POST /api/kpi/reports`, `/api/kpi/notifications`, `/api/kpi/activity`, `/api/kpi/requests`. Request: UTC millisecond `{since, until}`, start inclusive/end exclusive, maximum 90 days, end up to `KPI_MAX_CLOCK_SKEW_SECONDS` (currently 300 seconds) ahead of server time. Invalid periods return 400 after authorization. PostgreSQL reads use read-only transactions, a 10-second statement timeout, and a 10,000-group cap for report breakdowns; Greptime reads have connection/query and statement timeouts plus a 100,000-group response cap.
- [x] Report counts by period/type/author/UTC day from retained `report_history`, and worker generation median/p90 with valid/excluded sample counts. Counts are per row, not retry or download. Rows are selected by request creation time; statuses are current. The existing all-history successful total remains separately scoped. Any legacy-linked rows present in `report_history` count once; no legacy backfill or complete reconciliation is established. The separate legacy table is not independently added. Durations require a background-task ID, no legacy-log link, and nonnegative timestamps; synchronous completion and file archival timestamps do not measure generation and are excluded from durations while remaining in report counts. Worker durations include storing the result.
- [x] Optional host-scoped Greptime account/day/page observations. This source includes keep-alives, so these are explicitly observation metrics, not human engagement or DAU/WAU/MAU. UUIDs are deduplicated; legacy/unrecognized identities are excluded with an unmapped-group count. Show observed bounds and this process's queue counters; completeness is unknown. Empty/unconfigured telemetry is unavailable, and missing days are not zero-filled. The documented default retention is 30 days (`deploy/MIGRATIONS_GREPTIMEDB.md`), so a 90-day request does not imply 90 days of coverage.
- [x] Recorded API response totals, 4xx/5xx counts, status distribution, and error percentage from host-scoped `activity_details`. Count distinct request IDs per response status, excluding initial request events and records without a request ID. Request outcomes do not establish completed authentication attempts or system availability.
- [x] Load API-quality history as sequential browser requests for at most six hours each and aggregate totals/status counts in memory. Keep per-request backend deadlines; do not place the entire series behind one long HTTP request. Configured empty slices have zero recorded counts but remain unavailable as metrics; an unavailable source has unknown counts and stops the series without publishing partial totals. Commit only complete results, retain previous snapshots on failure, and abort obsolete series on period changes, refresh, or tab exit.
- [x] Messenger notification transport statuses and creation-to-sent median/p90 from `messenger_alert_delivery`. `sent` is the recorded transport stage, not confirmed device delivery/read. Zero retained jobs is a valid count; no duration samples is unavailable.
- [x] Independent source errors/retries, stale-response guards, retained response periods, typed Rust-generated frontend contracts, and explicit unavailable states for implemented metrics when their source data is missing.

The workstreams below retain their original scope: only the precise supported subsets above are delivered. Human engagement, authentication funnels, exact sessions, bot/report provenance, and instrumentation-dependent metrics remain unresolved.

## Existing-history workstream

- [ ] Before adding each historical metric, verify source availability, retention, event meaning, stable account identity, host isolation, missing/dropped events, and query cost. Use bounded server-side aggregation through an admin-only API in a separate implementation plan; do not connect the browser directly to Greptime/PostgreSQL or pass service credentials to it. Existing data may avoid new instrumentation, but still needs a supported read API.
- [ ] Define “active” from qualifying human actions, choose calendar vs rolling windows and timezone, and specify account/service/bot inclusion. Optional Greptime and its bounded, lossy activity queue require coverage indicators; unavailable history must display as unavailable, never as zero. A keep-alive alone does not prove interaction.

## Missing events, integrations, and product definitions

- [ ] Handle the remaining wishlist with explicit instrumentation/source work. Agree event definitions and ownership before selecting schemas or APIs; do not add blank or fabricated Iteration 1 charts for these metrics.

| Items from `idea.md` | Required evidence / product decision |
| --- | --- |
| Accounts deleted during a period | Timestamped account deactivation/permanent-deletion audit, including retained tombstones and the distinction between those operations. Current flags provide no deletion period. |
| UI interaction counts; misclicks; back navigation; button usage and unique users; rage clicks | Stable feature/control event IDs, distinct-user denominators, navigation context, and reviewed misclick/rage-click heuristics. Backend request counts and page heartbeats do not establish UI interactions. |
| Weekly login-support requests; top reasons (VPN, certificate, browser, password, device, frontline conditions); resolution time; repeated contacts | A support source with account linkage, opened/resolved times, and structured reason categories. Application login logs cannot establish support contacts or their resolution. |
| Failed connections uploaded later from the device | Client-side offline recording, bounded retry/deduplication, occurrence and upload timestamps, and a safe event schema. Server logs cannot observe requests that never arrived. |
| Seven-day activation; time to first key action; onboarding drop-off | Rada/product owner chooses the key action and ordered onboarding steps; capture qualifying actions and compute only fully observed seven-day cohorts. First-login metrics alone do not measure activation. |
| Which features people try | Rada/product owner supplies the feature list, eligible audience, and qualifying use event. Measure distinct users and adoption within that audience, not just clicks by one heavy user. |
| Report creation to recipient's first view: median/p90; reports no recipient opened | Explicit report-recipient identity, delivery/availability time, and first-view receipts. Loading an inbox or downloading a generated report does not prove the intended recipient opened the report. Define the observation window and unopened denominator. |
| Important reports without a reaction: no view, reply, or forward | A shared report/recipient identity plus importance, view, reply, and forwarding events and a reaction deadline. Define what qualifies as a reaction. |
| Page load time | Browser navigation/render/readiness timing with an agreed “ready” point; backend response duration covers only part of the experience. |
| Messages the bot did not pick up | Upstream expected-message inventory or sequence/cursor reconciliation against received messages. Missing messages cannot be counted from received messages alone. |
| New people added by colleagues | Retained creator/referrer identity on account creation or an equivalent audit source. Confirm referral meaning; do not infer a referrer from the account's current organism. |
| System availability | Independent checks over a defined service window and an agreed availability target; request logs cannot establish availability during periods with no traffic. |
